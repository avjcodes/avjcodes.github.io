    How this works, honestly

    No language model runs in this demo. The planner is a deterministic policy engine: a plain JavaScript function, nextAction(state), that inspects the run state and returns the next tool call. It drives the same loop shape a model-driven planner would drive: read the state, choose a tool, gather evidence, update, verify, stop.

    Measurements come from tools, never from generated text. Every number in the report, from a contrast ratio to a pixel of horizontal overflow, is read off the fetched page or the rendered sandbox at run time. If a tool cannot measure something, that lands in the uncertainties list instead of the findings.

    The sandbox is isolated. The audited page runs as a copy inside a sandboxed frame with an in-memory storage shim, so audit runs never touch the state the real demo pages keep in your browser. Dashed outlines in the preview are Site Doctor's inspection markers; green outlines are candidate fixes it patched in to verify.

    Production versions of this architecture put a model in the planner seat. That is the seat the policy function occupies here. The tools, the evidence discipline, the verification step and the stopping rules stay exactly the same; static hosting is why this page ships with the deterministic planner, and the audit is real either way.

    The loop

    1. 01Discover. Fetch the page, parse it, inventory links, forms, headings, controls.
    2. 02Goal. Map the business goal to concrete controls on the page.
    3. 03Test. Navigation, forms, accessibility, 375px layout, asset weight, and the goal flow end to end.
    4. 04Hypotheses. Findings raise testable claims; nothing ships as fact yet.
    5. 05Verify. Patch the sandbox, re-run the failing measurement, keep the before/after numbers.
    6. 06Report. Score severity against business impact, prioritize, state what remains unknown.
